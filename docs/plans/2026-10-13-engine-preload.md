# 첫 화면 형식 선택·엔진 백그라운드 내려받기·진행 화면 (2026-10-13)

PDF 뷰어 계획(`2026-10-13-pdf-viewer.md`)보다 먼저 한다. PDF 엔진은 PDF 계획 2단계에서 이 구조에 붙인다.

## 사용자 요청 (2026-10-13)

- 첫 화면에서 DOCX·HWPX·PDF 중 하나를 고른다.
- 첫 화면에 머무는 동안 엔진(WASM 등)을 백그라운드에서 내려받는다.
- 형식을 골랐을 때 그 엔진을 아직 다 받지 못했으면 "엔진 다운로드 중…" 진행 화면을 보여 준다.
- 이렇게 하면 Cloudflare 프록시를 켜도 접속 오류가 생기지 않는지 검토한다.

## 실측 (2026-10-13, `sketch-docs.pages.dev`, 서비스 워커 막고 새 컨텍스트, ICN)

| 화면 | 준비까지 | 전송량 | 300KB 넘는 파일 |
|---|---|---|---|
| `/` | 3.2초 | 25KB | 없음 |
| `/word` | 3.7초 | 1,730KB | Word 엔진 JS 653KB |
| `/hwp` | 4.1초 | 4,663KB | rhwp WASM 4,069KB(br), rhwp JS 406KB |

- 빌드 결과에 있는 큰 파일(harper WASM 16MB, 사전·유의어 사전, canvaskit 7.3MB)은 편집기를 처음 열 때 받지 않는다.
- 프록시를 켰을 때 KT 회선 실측
  - 같은 WASM이 날에 따라 2.4~3.7초, 나쁠 때는 90초에 4MB(약 44KB/s)였다.
  - 44KB/s라면 한글 엔진 4.7MB가 약 110초, Word 엔진 1.7MB가 약 40초 걸린다(계산값).

## 프록시를 켜도 되는가 — 검토

1. **앱 오류는 원래 없었다.** 앱에는 엔진 로딩 시간 상한이 없다. 느린 회선에서도 결국 열리고, 실패한 것은 시험의 대기 한도(30~40초)였다. 사용자가 본 현상은 "오류"가 아니라 아무 표시 없이 오래 기다리는 화면이다.
2. **이 변경으로 해결되는 것:** 기다리는 동안 진행률이 보인다. 첫 화면에 머무는 시간만큼 미리 받으니 그만큼 기다림이 준다. 연결이 멈추면 다시 시도할 수 있다.
3. **해결되지 않는 것:** 경로가 느리면 전송 속도는 그대로다. 첫 화면에서 바로 고르면 44KB/s 경로에서 한글 엔진은 여전히 2분 가까이 걸린다.
4. **새로 생기는 위험:** 세 엔진(약 6.4MB, PDF 추가 시 더 늘어남)을 한꺼번에 받으면 느린 회선에서 대역폭을 나눠 쓰게 된다. 그러면 고른 엔진이 오히려 늦게 받아진다. 그래서 고르는 순간 나머지 내려받기를 멈추고 고른 엔진만 받는다.
5. **결론(예상):** 프록시를 켜도 "오류"는 생기지 않고 진행 화면이 보이게 된다. 다만 첫 방문 대기 시간은 DNS only보다 길다. 그래서 **DNS only를 유지하는 것을 권한다.** 이 변경은 느린 모바일 회선에서도 쓸모가 있으므로 프록시와 상관없이 한다.
   - 5단계에서 Chrome 네트워크 제한(50KB/s, 500KB/s)으로 재서 이 예상을 확인하고 결과를 여기에 적는다.

## 완료 조건 (DoD)

1. 첫 화면에 DOCX·HWPX·PDF 카드 세 개가 있다.
   - PDF 카드는 PDF 엔진이 들어올 때 붙인다. 그전에는 두 개다.
   - HWPX 카드는 HWP 파일도 연다고 적는다.
2. 백그라운드 내려받기
   - 첫 화면을 띄운 뒤 브라우저가 한가해지면 엔진 파일을 우선순위 낮게 하나씩 받는다.
   - 순서: 이 브라우저에서 마지막으로 쓴 형식이 먼저, 없으면 DOCX → HWPX → PDF.
   - 데이터 절약 모드(`navigator.connection.saveData`)나 2G 계열 회선에서는 미리 받지 않는다.
   - 받은 파일은 브라우저 HTTP 캐시에 들어간다. 편집기는 같은 URL을 캐시에서 바로 쓴다(이미 immutable 헤더가 있음).
3. 형식을 고르면 다른 엔진의 미리 받기를 멈추고 고른 엔진만 받는다.
4. 진행 화면
   - 고른 엔진의 필수 파일을 다 받지 못했으면 "엔진 다운로드 중… 2.1 / 4.7MB"와 진행 막대를 보여 준다.
   - 다 받았으면 진행 화면 없이 바로 편집기로 간다.
   - 15초 동안 받은 바이트가 없으면 "연결이 느립니다. 다시 시도" 버튼을 보여 준다. 오류로 끊기면 같은 화면에서 다시 시도할 수 있다.
   - 헤더의 W·한 전환으로 처음 여는 엔진에도 같은 진행 화면을 쓴다.
5. 엔진 필수 파일 목록(manifest)
   - 빌드가 엔진별 필수 파일 목록과 크기(압축 전·후)를 `engines.json`으로 만든다.
   - 시험: Chrome에서 각 편집기를 열 때 요청한 100KB 넘는 같은 출처 파일이 모두 목록에 있어야 한다. 원본 업데이트로 엔진이 새 파일을 요구하면 시험이 실패한다.
6. 오프라인 Word, 서비스 워커, 기존 통합·회귀 시험이 모두 그대로 통과한다.
7. 첫 화면 진입 전송량은 미리 받기를 빼면 지금(25KB)과 비슷하다. 진행 화면 코드는 작게 유지한다.

## 범위 밖

- 엔진 크기 자체 줄이기(WASM 최적화, 원본 변경)
- 서비스 워커로 한글·PDF 엔진 오프라인 캐시

## 설계

- `scripts/build-engines.mjs`(또는 새 `scripts/engine-manifest.mjs`)가 빌드된 `dist/engines/word/index.html`과 rhwp `index.html`에서 진입 JS·CSS를 찾는다. 여기에 진입 JS가 `new URL('…wasm', import.meta.url)`로 부르는 WASM을 더해 `engines.json`을 만든다.
  - 목록이 정확한지는 DoD 5의 Chrome 시험이 판정한다. 빌드 스크립트의 추정을 믿지 않는다.
- `src/enginePreload.ts`
  - `preload(engine, {signal, onProgress})`: 목록의 파일을 `fetch(url, {priority: 'low' | 'high'})`로 받는다. 본문을 끝까지 읽으며 바이트를 센다.
  - 같은 URL은 한 번만 받는다(진행 중 Promise 공유). 고르면 다른 엔진의 `AbortController`를 멈추고, 고른 엔진은 `high`로 다시 요청한다.
- 첫 화면(`home.ts`): `requestIdleCallback` 뒤에 백그라운드로 받기 시작한다. 카드 클릭은 지금처럼 일반 링크로 둔다.
  - 다음 페이지(셸)가 다시 `preload()`를 부른다. 받은 파일은 HTTP 캐시에서 곧바로 끝나고, 덜 받은 파일만 이어서 받는다(이어받기가 아니라 처음부터 다시 받는다 — 한계로 기록).
- 셸(`EditorShell`): 엔진 iframe을 만들기 전에 `preload(engine)`를 기다리며 `EngineProgress.svelte`를 보여 준다. 끝나면 iframe을 만든다.
- 서비스 워커: Word 엔진 파일은 지금처럼 fetch 핸들러가 Cache Storage에도 넣는다. 한글은 지금처럼 제외한다.

## 단계

1. **manifest와 검사 시험.** `engines.json` 생성, Chrome으로 요청 목록과 대조하는 회귀 시나리오. 시험이 실패하게 목록에서 파일 하나를 빼 보는 변이도 돌린다.
2. **`enginePreload.ts`와 단위 시험.** 가짜 fetch로 확인한다: 바이트 집계, 중복 요청 공유, 중단, 정체 감지, 실패 뒤 다시 시도.
3. **셸 진행 화면.** iframe 생성을 preload 뒤로 옮긴다. 회귀 시험은 네트워크 제한 상태에서 진행 화면과 숫자가 보이는지, 다 받은 뒤 편집기가 열리는지 확인한다.
4. **첫 화면 카드·백그라운드 받기.** 회귀 시험
   - 첫 화면에서 기다린 뒤 `/hwp`로 가면 진행 화면 없이 열린다.
   - 바로 고르면 다른 엔진 요청이 중단된다.
   - saveData면 미리 받지 않는다.
5. **실측과 판정.** Chrome 제한 50KB/s·500KB/s·제한 없음에서 첫 화면 → 형식 선택 → 편집기 준비 시간을 잰다. 위 "검토"의 예상과 대조해 적는다. `npm run verify`를 돌리고, Codex 코드 리뷰를 2회 받는다.

## 위험

- **목록 밖 파일:** 원본 업데이트로 엔진이 필수 파일을 바꾸면 진행률이 틀리거나 iframe이 다시 받는다. DoD 5 시험이 잡는다.
- **캐시 공유:** `fetch()`로 받은 응답을 iframe 안의 `<script type=module>`·WASM 요청이 같은 HTTP 캐시 항목으로 쓰는지는 Chrome에서 실측하지 않았다. 3단계 시험에서 두 번째 요청의 `fromDiskCache`/`fromMemoryCache`를 확인한다.
- **압축 크기:** 진행률 분모는 전송 크기(br)여야 맞다. 빌드가 아는 것은 압축 전 크기다. `Content-Length`가 없으면(br 동적 압축) 압축 전 크기 대비로 보여 주고, 표시는 "약"으로 한다.
- **모바일 데이터:** 미리 받기는 사용자가 원하지 않은 데이터를 쓴다. saveData·2G 예외 외에, 미리 받는 양의 상한을 둘지 1단계 수치를 보고 정한다.
