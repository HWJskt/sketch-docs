# P0 기준선과 P1 한글 웹 실행 첫 구현

확인일: 2026-10-11. 전체 개발 목표의 완료 보고서가 아니라 P1 첫 구현 기록이다.

구현 커밋: edentext `59df5588`. 계획 문서는 사용자 지정 위치인 프로젝트 최상위 `docs/`에 있으며 edentext 저장소 밖이다. 기존 계획 문서 이동으로 생긴 삭제 상태 3건은 이번 구현 커밋에 포함하지 않았다.

## 구현한 범위

- edentext의 `/hwp.html`에 한글 검증 화면을 추가했다. 기존 Word 편집기는 `/`에 유지하며 아직 두 화면의 공통 세션·메뉴 통합은 하지 않았다.
- rhwp v0.8.7, 커밋 `1a76570e833917d15817415a53c09ad61ab3203f`와 HOP에서 검증된 WASM을 사용한다. `scripts/build-rhwp.mjs`가 원본을 수정하지 않고 임시 사본에 제품 확장을 적용해 `public/rhwp/`를 만든다. 폰트와 WASM은 로컬 제공하며 외부 웹폰트를 비활성화했다.
- 같은 origin의 iframe에 한정한 `edentextHost` 확장을 추가했다. 새 문서 생성/열기 완료를 기다리고, 같은 내보내기에서 바이트·손실 보고·epoch/revision을 반환한다. 저장 완료 시 버전이 일치할 때만 clean으로 바꾼다. 공개 SDK/RPC 확장으로 일반화한 상태는 아니다.
- 호스트에서 파일 선택과 스트림 쓰기를 수행한다. 손실 보고, 외부 변경, 확장자 불일치와 실패를 처리한다. 다른 이름 저장 성공 뒤 일반 저장은 새 파일을 대상으로 한다.
- 가져온 원본의 덮어쓰기는 보존 검증 전까지 차단한다. 새 문서 또는 별도 저장한 파일의 재저장은 가능하다. 자동 복구와 DOCX 변환은 아직 제공하지 않는다.
- 한글 검증 화면·엔진은 기존 DOCX 서비스 워커 캐시를 우회한다. 다른 HTML이 DOCX 오프라인 시작 화면으로 저장되는 문제를 방지한다. 한글 오프라인 지원을 완료한 것은 아니다.

## 실행

프로젝트에는 `source/edentext`와 준비된 `source/hop`가 함께 있어야 한다. `npm ci`만으로 rhwp 소스가 내려받아지지는 않는다. 향후 CI에서도 고정된 HOP/rhwp를 준비하는 절차가 필요하다.

```sh
cd /Users/hwjung/Coding/edentext-word-hwp/source/edentext
volta run --node 24.21.0 npm run dev -- --host localhost --port 5173 --strictPort
```

- Word 화면: `http://localhost:5173/`
- 한글 검증 화면: `http://localhost:5173/hwp.html`
- 배포용 빌드: `volta run --node 24.21.0 npm run build`
- 배포용 로컬 검사: `volta run --node 24.21.0 npm run test:hangul` — 설치된 Chrome과 비어 있는 4173 포트 필요. 검사 자체가 서버와 브라우저를 열고 종료한다.

한글 브라우저 검사는 다음을 실행했다.

1. 배포용 Word 화면과 서비스 워커를 먼저 로드한 다음 한글 화면을 연다.
2. 새 문서에 `한글 편집 검증 ABC 123`과 2×2 표를 UI로 작성한다.
3. HWP 13,312바이트, HWPX 7,938바이트를 내보낸다. 두 결과의 손실 보고는 각각 0건이다.
4. 각 형식을 다시 열어 HWPX XML에서 본문과 2×2 표 구조를 확인한다. 이는 한컴 렌더 결과와의 일치 증거는 아니다.
5. 내보낸 뒤 추가 편집한 상태에서 오래된 저장 ACK를 보내 거부와 dirty 유지를 확인한다.
6. 손상 파일과 암호 문서가 대화상자 대기에 갇히지 않고 거절되며 이전 epoch/revision/dirty가 유지되는지 확인한다.
7. 실제 OPFS 파일 핸들을 OS 선택기 대신 공급하여 호스트의 저장 버튼을 검사한다. 외부 변경은 보존하고, 가져온 원본 덮어쓰기는 차단하며, 다른 이름 저장 후 재저장은 사본에 반영되는지 확인한다.
8. DOCX 캐시의 시작 HTML이 한글 화면으로 덮어써지지 않는지 확인한다. 관측한 한글 작업 중 외부 HTTP 요청과 uncaught 오류는 0건이다.

자동화의 한글 입력은 `keyboard.insertText`로 수행했다. 실제 한국어 IME 조합 키 입력은 수동 확인 대상으로 남긴다. OPFS는 브라우저 전용 저장 영역이므로 위 파일 쓰기 검사를 사용자 로컬 디스크 저장의 완료 증거로 취급하지 않는다.

산출물은 `source/edentext/debug/hangul/`에 생성된다: `edited.png`, `new.hwp`, `new.hwpx`, `host-saved.hwpx`, `result.json`. debug 산출물은 Git 추적에서 제외된다. 편집 화면 PNG를 직접 확인해 본문 표시를 점검했다.

빌드에는 기존 큰 청크·CSS 처리 경고와 CanvasKit의 브라우저용 Node 모듈 externalization 경고가 남는다. 현재 사용한 Canvas2D 경로가 동작하는 것을 확인했으며 CanvasKit 렌더러 전체 검증은 하지 않았다.

## 독립 검토와 남은 작업

읽기 전용 별도 에이전트가 암호 대화상자의 inert 대기, 손상 파일 열기 실패 뒤 화면 복구 누락, 초기화 예외 삼키기를 지적했다. 제품 빌드 확장에서 암호 문서를 명시적으로 거절하고 초기화 오류를 전파하도록 수정했다. 파싱 실패 시 기존 뷰를 복구하며, 문서 generation이 바뀐 뒤 실패하면 이전 저장 대상 연결을 해제한다. 재검토에서 이 수정 경로를 확인했다.

다음 구현은 P1의 최소 DOCX↔HWPX 변환 실증과 P2/P3의 공통 세션·저장 통합이다. 아직 남은 항목:

- OS 파일 선택기에서 실제 파일 열기·저장·다른 이름 저장과 권한 재요청.
- 가져오기 단계 손실·보호 속성 판정과 원본 덮어쓰기 허용 기준.
- 실제 Word·한컴에서 재열기 및 화면·내용 비교, Windows/Edge 검사.
- 문서 초기화 실패 주입, 모든 편집 경로의 revision 추적, IME 조합 중 저장.
- 복구·복제 탭 쓰기 조정, 공통 UI, DOCX/HWPX 변환과 고급 문서 요소.
- 기존 서비스 워커에서 v4로의 갱신 실측과 배포 환경 검사.

시험용 서버와 브라우저는 검사 후 종료했다. 라이브 배포와 원격 push는 수행하지 않았다.
