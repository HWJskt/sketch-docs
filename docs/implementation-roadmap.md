# Word와 한글 웹에디터 구현 계획

기준일: 2026-10-11

이 문서의 소스·테스트 경로는 별도 표기가 없으면 `source/edentext/`를 기준으로 한다. 계획 문서는 프로젝트 최상위 `docs/`에서 관리한다.

[최종 개발 목표](project-goals.md)를 구현하기 위한 실행 계획이다. [기술 스택 제안](architecture/web-editor-stack.md)의 Svelte·TipTap·rhwp 구성을 검증 기준 후보로 사용한다. 각 단계의 완료는 이후 단계와 전체 제품의 완료를 의미하지 않는다.

## 우선순위와 구현 원칙

개발과 사용자 확인은 localhost에서 먼저 진행한다. 개발 서버 검사와 배포용 빌드의 로컬 검사를 모두 통과한 뒤 사용자가 실제 파일 작업을 확인한다. 그 전에는 라이브 배포하지 않는다. 실행 순서·시연 항목·배포 전 통과 조건은 [localhost 개발·검증 계획](local-validation.md)을 따른다.

우선순위는 로컬 파일과 작업 내용 보호, 실제 형식별 저장, 문서 보존, 일관된 편집 경험, 형식 변환 확장, AI 순서다. 새 문서의 DOCX·HWPX 저장은 핵심 요구이므로 최소 변환 경로를 마지막 단계로 미루지 않는다.

초기에는 한 브라우저 탭에 활성 문서 하나를 유지한다. 현재 `storage/docScope.ts`는 모듈 초기화 때 `docId`를 결정하고 여러 모듈이 이 값을 사용한다. 기존 브라우저 탭별 격리를 유지한 상태에서 엔진을 연결하고, 앱 내부 문서 탭은 문서별 상태 분리가 검증된 뒤 제공한다. 최종 목표의 여러 문서 작업은 유지한다.

실증 실패 시 어댑터나 엔진 경계를 재검토한다. 지원되지 않는 기능을 조용히 제외하거나 `.hwp` 저장을 `.hwpx` 다운로드로 대체해 통과 처리하지 않는다.

## P0 기준선과 지원 표

산출물은 기존 동작의 검사 결과, 문서군 목록, 기능별 지원 표, 고정 의존성 목록이다.

- 현재 DOCX/ODT 열기·편집·저장·다른 이름 저장·새 문서·복구 동작을 기록한다. 기존 type check·단위 검사·관련 브라우저 검사를 실행하고 선재 실패를 구분한다.
- 개인정보 없는 합성 문서와 재배포 가능한 샘플을 준비한다. 본문, 혼합 서식, 한글·영문, 목록, 병합 표, 여러 쪽 표, 표 안 그림, 글상자, 수식, 머리말·꼬리말, 구역을 독립적으로 식별한다.
- 각 샘플에 텍스트와 순서, 셀 구조, 이미지 해시, 서식 구간, 용지 설정, 참조 렌더와 사용 글꼴을 기록한다. 실제 업무 문서의 이름이나 개인정보는 저장소에 넣지 않는다.
- 기능표는 형식별로 읽기·표시·편집·동일 형식 저장·교차 형식 변환을 구분한다. `지원`, `손실 안내 후 별도 저장`, `차단`, `미검증`을 사용한다.
- 암호화·전자서명·배포용 문서 등 보호 속성의 감지와 보존 가능 여부도 형식별로 기록한다. 미지원 보호 속성은 원본 저장을 차단하고 암호화 해제나 서명 제거를 조용히 수행하지 않는다.
- 첫 완전 지원 검증 대상은 Windows/macOS의 데스크톱 Chrome·Edge로 제안한다. Safari/Firefox는 편집과 다운로드의 제한 지원을 별도 검증한다.
- Word·한컴 실검증 환경을 확보한다. 확보하지 못한 항목은 미검증으로 남기고 호환성 완료를 선언하지 않는다.

통과 조건: 기존 DOCX/ODT 기준선과 재현 가능한 문서군을 확보하고, 필수 검사에 사용할 실제 프로그램·브라우저 환경을 명시한다.

## P1 가장 불확실한 경로의 실증

제품 전체 리팩터링 전에 작고 폐기 가능한 실증 경로로 다음 세 가지를 확인한다.

1. 고정 버전 rhwp Studio·SDK·WASM·글꼴을 자체 호스팅해 HWP와 HWPX를 열고 한글 본문·표를 수정한다. 각각 원래 형식으로 로컬 저장하고 한컴에서 다시 연다.
2. 빈 문서를 만든 뒤 본문·기본 서식·일반 표를 작성한다. DOCX와 HWPX 양방향 최소 변환을 수행해 두 형식으로 저장하고 양쪽 프로그램에서 확인한다. 엔진을 선택해야만 특정 형식으로 저장할 수 있는 구현을 최종 설계로 확정하지 않는다.
3. rhwp에서 동일 직렬화의 바이트·내용 손실 보고·문서 버전을 함께 반환하고, 특정 버전의 저장 완료만 통지하는 브리지를 실증한다. 현재 byte-only export와 전역 clean 통지만으로 제품 저장 계약을 충족한다고 가정하지 않는다.

새 문서 생성은 rhwp의 공개 생성 명령과 빈 문서 초기화를 확인한다. 읽기 전용 샘플을 편집해 저장하는 성공을 새 문서 생성 성공으로 대체하지 않는다. 변환 시 이미지나 복잡한 서식이 아직 미지원이면 생성 UI가 해당 요소를 지원한다고 표시하지 않는다.

통과 조건: 두 엔진의 저장과 최소 양방향 변환, 새 문서 생성, 버전 지정 저장 확인이 실제 파일로 입증된다. 실패 항목은 원인·대안·비용을 기록하고 P2 확대 전에 해결한다.

## P2 문서 세션과 엔진 어댑터

다음 경로는 구현 시 사용할 제안이며 기존 책임과 중복되면 기존 모듈에 통합한다.

| 경로 | 책임 |
|---|---|
| `src/lib/document/types.ts` | 형식, 문서 세션, 엔진 capability, 저장 산출물과 진단 계약 |
| `src/lib/document/session.ts` | 문서 생명주기, 문서 버전, 파일 연결, 변경 상태 |
| `src/lib/document/saveCoordinator.ts` | 저장 트랜잭션, 충돌·취소·실패, 완료 반영 |
| `src/lib/engines/tiptapAdapter.ts` | 기존 편집기와 import/export를 공통 명령에 연결 |
| `src/lib/engines/rhwpAdapter.ts` | 임베드 연결, 명령·변경 이벤트, 내보내기·종료 |
| `src/lib/components/HwpxEditor.svelte` | HWP/HWPX 공용 Studio 컨테이너의 마운트·표시·해제 |
| `src/lib/conversion/` | 명시적 형식 변환과 기능별 손실 진단 |

세션에는 고유 ID, 엔진 종류, 현재 파일 형식, 파일 핸들, 파일 fingerprint, 문서 epoch/revision, 저장된 revision, 복구 snapshot 버전을 구분한다. 새 파일 열기와 복구는 epoch를 바꾸며, 이전 epoch에서 도착한 이벤트나 비동기 결과를 현재 문서에 적용하지 않는다.

보호 속성과 감지 확실성도 세션에 보관한다. 암호를 영속 저장하지 않고 형식별 보호 기능을 내보내기 전에 검사한다. 보존할 수 없는 보호는 원본 저장을 차단한다. 보호 해제본 생성은 명시적인 별도 선택으로만 허용하고 사용자에게 결과의 보호 상태를 표시한다. 기존 ODT/DOCX 암호화를 HWP/HWPX에 재사용하지 않는다.

revision의 증가 범위에는 본문뿐 아니라 서식·표 구조·페이지 설정·머리말·이미지 변경을 포함한다. 내보내기는 불변 snapshot을 사용하거나 동기 직렬화 구간을 보장한다. 비동기 내보내기가 도중의 변경을 섞을 수 있으면 결과를 폐기하고 재시도한다. 임의의 과거 revision을 엔진이 다시 생성할 수 있다고 가정하지 않는다.

어댑터는 `create`, `open`, `execute`, `getState`, `subscribe`, `export`, `snapshot`, `dispose`에 해당하는 책임을 제공한다. 반환 데이터와 명령의 실제 이름은 P1에서 확인한 공개 API에 맞춘다. `unsupported`와 실행 실패를 구분하며, 모르는 기능을 성공으로 응답하지 않는다.

`open` 결과에는 가져오기 단계의 손실·미지원 요소·확인할 수 없는 보존 항목을 포함한다. 원본 바이트와 진단을 문서 세션에 보관하고 편집·내보내기 진단과 합쳐 원본 저장 가능 여부를 판단한다. 열기에서 이미 사라진 요소를 내보내기 경고 0건으로 무손실 판정하지 않는다. 보존 여부를 판정할 수 없는 원본은 별도 저장을 기본으로 한다.

문서 본문뿐 아니라 스타일, 머리말·꼬리말, 페이지 설정, 이미지·글꼴, AI 기록도 문서 소유 상태로 분류한다. 기존 모듈 전역 상태를 제거하는 작업은 동작 변경과 분리해 기존 DOCX/ODT 동작의 동등성을 검사한다.

통과 조건: 한 문서에서 엔진을 교체해도 이전 문서 상태가 섞이지 않고, 기존 DOCX/ODT 기능 검사가 유지된다. 늦게 도착한 열기·저장·복구·AI 응답이 다른 문서를 바꾸지 않는다.

## P3 로컬 저장과 최초 저장

파일 I/O는 상위 앱이 소유한다. iframe의 자체 파일 메뉴는 공통 파일 명령으로 연결하거나 숨겨 중복 저장 경로를 없앤다. 사용자 클릭에 필요한 파일 선택기·권한 요청을 상위 문서에서 실행하고 문서 내용만 엔진과 교환한다.

저장은 아래 순서의 트랜잭션으로 처리한다.

1. 문서 세션·revision·출력 형식·대상 핸들을 정한다. 같은 세션과 같은 파일에 대한 중복 저장을 직렬화하고, 다른 이름 저장과 일반 저장도 순서를 보장한다.
2. 저장 선택기가 필요하면 형식 선택 후 새로운 사용자 클릭에서 바로 호출한다. 취소하면 다운로드로 우회하지 않는다. 파일 핸들을 받은 것만으로 현재 문서의 연결을 바꾸지 않는다.
3. 지정한 revision의 내보내기 바이트와 손실 진단을 얻는다. 내용 손실 시 원본 갱신을 중단하고 별도 저장이나 취소를 안내한다. 파일 이름 확장자만 바꾸지 않고 실제 바이트 형식과 일치시킨다.
4. 쓰기 직전 대상 파일의 외부 변경 여부를 재확인한다. 같은 파일 판단에는 핸들 identity를 사용하고 파일명만으로 판단하지 않는다. 충돌은 다시 열기·별도 저장·명시적 덮어쓰기로 처리한다.
5. 스트림 기록과 닫기가 성공하면 저장된 revision과 파일 연결을 반영한다. 실패하면 스트림을 정리하고 기존 연결과 미저장 편집을 보존한다. 여러 브라우저 탭의 같은 파일 저장도 조정하고 외부 프로그램과의 완전한 잠금은 보장하지 않는다.
6. 기록한 revision보다 최신 변경이 있으면 dirty를 유지한다. 저장된 바이트보다 최신 복구본을 삭제하지 않는다. 파일 저장 성공 뒤 최근 파일 메타데이터 기록 실패는 디스크 저장 실패와 구분한다.

지원하지 않는 브라우저는 다운로드임을 표시한다. 드롭한 File에 원본 핸들이 없으면 핸들을 얻을 수 있는 API를 사용하거나 첫 저장에서 대상 선택을 받는다. IndexedDB 핸들 복원 뒤에도 사용자 클릭에서 권한을 재확인한다.

기존 `storage/recentFiles.ts`에는 핸들이 일치하지 않아도 이름이 같으면 최근 파일 ID를 재사용하는 경로가 있다. 서로 다른 폴더의 동명 문서를 별도 항목으로 유지하도록 정리하고, 최근 파일 ID를 공유한 두 세션이 다른 원본에 저장하지 않는지 검사한다.

다른 형식으로 저장할 때는 한글 조합 입력을 확정하고 사용자 입력과 AI를 포함한 문서 변경을 잠시 제한한 뒤 revision을 고정한다. 변환 결과를 새 세션 후보로 만들어 재열기를 검증한 다음 파일을 저장한다. 이후 편집에 대상 엔진이 필요하면 저장 성공 뒤 준비된 후보로 활성 세션과 파일 연결을 전환하고 입력을 다시 허용한다. 취소·실패 시 원래 세션으로 복귀하고 입력을 복원한다. 다른 이름으로 저장이 성공하면 다음 일반 저장은 반드시 새 파일을 대상으로 한다.

원래 세션과 복구본은 전환 성공까지 보존한다. 전환 후 undo가 원래 엔진의 이력까지 이어지는 것으로 표시하지 않으며, 기존 편집 상태는 별도 복구 가능 상태로 남긴다. 편집을 계속하면서 특정 revision을 별도로 저장하는 기능이 필요하면 이를 `사본 내보내기`로 구분하고 `다른 이름으로 저장`의 파일 연결 전환 계약을 바꾸지 않는다.

통과 조건: 개발 목표의 로컬 저장 흐름과 취소·권한 거부·외부 변경·저장 중 편집 시나리오가 실제 파일에서 통과한다.

## P4 복구와 여러 문서

기존 localStorage·이미지 저장소·스냅샷을 곧바로 일괄 이관하지 않는다. 새 문서 세션 저장 계약을 먼저 도입하고, 버전이 명시된 IndexedDB 레코드로 점진적으로 이관한다. 이관 실패 시 원래 데이터를 읽을 수 있게 보존한다. 사용자의 `keep`, `closed`, `none` 보존 설정을 두 엔진에 동일하게 적용한다.

문서 ID와 브라우저 탭 인스턴스 ID를 분리하고 복구본 쓰기 소유권을 정한다. 기존 sessionStorage의 ID가 복제 탭으로 복사되어도 두 탭이 같은 복구본을 덮어쓰지 않도록 한다. Web Lock을 사용할 때는 획득 완료 전에 해당 복구본의 쓰기를 시작하지 않는다. 소유권이 없는 탭은 별도 세션 사본을 만들거나 읽기 전용으로 열며, 탭 복제·동시 편집·한쪽 종료·새로고침·잠금 미지원 환경을 검사한다. 로컬 파일 쓰기 조정과 복구본 소유권은 별도의 계약이다.

복구본은 문서 ID·epoch·revision·엔진 버전·파일 연결 정보를 갖는다. rhwp 복구에 저장용 파일을 사용할 때도 손실 보고를 확인한다. 저장 직렬화가 모든 편집 상태를 보존하지 못하면 전용 snapshot API를 사용하거나 원본과 검증된 편집 로그를 유지하는 경로를 P1/P2에서 정한다. lossy export를 정상 복구본으로 간주하지 않는다.

호스트와 Studio의 자동 저장을 동시에 독립 운영하지 않는다. 저장·복구 책임자는 하나로 정하고 다른 경로를 비활성화하거나 같은 세션 계약에 연결한다. 종료 이벤트의 비동기 작업만 믿지 않고 편집 중 주기적으로 복구본을 저장한다. quota 초과·복구 실패를 사용자에게 알린다.

그 뒤 앱 내부 문서 탭을 도입한다. 초기 구현에서는 엔진별 인스턴스를 컨테이너에 유지하고 CSS로 표시를 전환한다. 메모리 사용이 큰 비활성 탭의 해제는 복구 snapshot과 재열기 보존 검증이 끝난 뒤 도입한다. 저장 중인 문서 종료와 AI 응답을 포함한 pending 작업을 명시적으로 처리한다.

통과 조건: 두 엔진의 문서 전환·브라우저 새로고침·중단 복구·보존 설정이 맞게 동작하고 문서 간 이미지·설정·파일 핸들이 섞이지 않는다.

## P5 공통 UI와 변환 확장

UI는 열기·저장·다른 이름 저장·새 문서, 실행 취소·찾기, 문자·문단 서식, 표·이미지, 고급 문서 설정 순으로 통합한다. 명령 실행뿐 아니라 enabled·selected·mixed 상태, iframe 포커스·클립보드·한글 IME·단축키·접근성도 연결한다. 지원하지 않는 명령은 동작하는 것처럼 노출하지 않는다.

변환 계층은 두 엔진의 전체 문서 모델을 통일하지 않고, 변환에 필요한 구조를 정의한다. 텍스트·run 서식·문단·목록·표/병합·이미지부터 시작해 구역·머리말·글상자·수식으로 확장한다. 각 요소의 방향별 매핑과 손실 진단을 기능표에 기록한다. HTML이나 Markdown을 최종 교환 형식으로 사용해 문서 고유 구조를 버리지 않는다.

HWP 입력은 rhwp 모델/HWPX 출력의 보존 범위를 확인하고 변환 경로를 선택한다. DOCX에서 HWP로 가는 경우 DOCX→HWPX→rhwp→HWP 경로의 각 단계에 대해 별도로 손실을 검사한다. 경고 0건을 완전 보존의 증거로 삼지 않고 독립 내용 비교와 실제 프로그램 렌더 검사를 병행한다.

통과 조건: 기능표의 최종 지원 요소와 개발 목표의 형식 간 변환을 검증하고, 별도 저장과 엔진 전환 이후의 편집·저장 동작까지 확인한다.

## P6 AI 연결과 최종 배포

라이브 배포의 선행 조건은 localhost 배포용 빌드 검증과 사용자 확인이다. 로컬 검증 완료만으로 배포를 실행하지 않으며, 배포 대상과 명시적인 배포 요청이 정해진 뒤 진행한다. localhost 검증이 운영 HTTPS·캐시·경로 설정 검사를 대신하지는 않는다.

기존 TipTap AI 도구와 rhwp 명령을 공통 사용자 흐름에 연결하되 엔진별 capability를 존중한다. 문서·선택·revision을 기준으로 후보를 만들고, 검토·적용·취소·충돌 검사를 제공한다. 본문 제한 API를 표·혼합 서식까지 지원하는 것으로 간주하지 않는다. 필요한 공개 명령 확장과 검사를 별도 작업으로 둔다.

제품 배포는 HTTPS 정적 자산으로 시작한다. 앱·SDK·Studio·WASM·글꼴의 버전 조합과 무결성을 기록하고, 캐시 갱신 중 서로 다른 버전이 섞이지 않게 한다. 원격 데모 의존, 불필요한 외부 글꼴 요청, 기본 문서 작업의 원문 전송이 없는지 네트워크 검사한다. PWA는 이후 별도 기능으로 평가한다.

통과 조건: 브라우저/OS 지원표, 문서 기능표, 손실 안내, 복구·권한 동작, Word·한컴 검증 결과와 알려진 제한을 갖춘다. 실제 파일 검증을 수행하지 못한 조합은 지원 완료로 표시하지 않는다.

## 검사 설계

| 검사 | 주요 시나리오 |
|---|---|
| 로직 | epoch/revision, 중복 저장, 상태 전이, 파일 identity, 변환 매핑과 손실 진단 |
| 브라우저 | 열기·최초 저장·다른 이름 저장, 선택기 사용자 활성화, iframe 포커스·명령, 문서 전환 |
| 장애 주입 | 선택기 취소, 권한 거부, write/close 실패, IndexedDB 실패, 엔진 중단, 늦은 응답 |
| 실제 OS | 로컬 원본 변경, 권한 재요청, 한글 조합 입력, 파일 연결 복구 |
| 문서 왕복 | 앱 자체 재열기, Word·한컴 재열기·재저장, 텍스트/표/이미지/서식 비교 |
| 시각 | 기준 글꼴에서 쪽 수·잘림·겹침·표 분할·줄바꿈 비교, 엔진별 차이 기록 |
| 기존 회귀 | DOCX/ODT import/export, 기존 브라우저 편집과 복구 |

목표 수치는 P0에서 문서군과 환경을 고정한 뒤 정한다. 입력 크기·ZIP 팽창·XML 깊이·WASM 메모리·시간 제한은 파서 경계에 적용하고, 손상 문서와 한도를 넘는 문서에서 작업 중인 다른 문서를 보존한다.

## 작업 분할과 검토 운영

작업 단위는 P0 기준선, P1 rhwp 입출력, P1 최소 양방향 변환, P2 세션 계약, P2 각 어댑터, P3 파일 저장, P4 복구, P4 문서 탭, P5 UI 명령군, P5 변환 요소군, P6 AI/배포로 나눈다. 각 단위는 관련 검사와 함께 독립적으로 검토한다. 공통 계약이 바뀌면 소비자와 검사 변경을 함께 명시한다.

현재 세션에서 사용자는 Herdr 오른쪽 pane에 `codex --yolo`로 역할별 에이전트를 실행하는 것을 허용했다. 계획·저장 검토와 향후 구현 분담에 활용할 수 있다. pane ID나 에이전트 실행 상태는 영속적인 프로젝트 설정으로 취급하지 않는다.

- 조정 역할은 범위·공통 타입·문서·통합을 소유한다.
- 엔진 역할은 rhwp 어댑터·Studio 경계, 저장 역할은 파일 I/O·세션·복구를 담당할 수 있다.
- 검증 역할은 독립적으로 내용 보존·실제 프로그램 호환성을 검사한다.
- 같은 파일을 동시에 편집하지 않는다. 공유 파일은 한 담당자만 수정하고 나머지는 제안으로 전달한다. 검토 에이전트는 읽기 전용으로 운영한다.
- 세션·서버·pane은 이번 작업에서 만든 것만 관리한다. 작업 종료 때 생성한 에이전트와 테스트 프로세스의 종료를 확인한다.

이 문서는 구현 착수 전 계획이다. 첫 실행 작업은 P0 기준선과 P1 실증이며, 구현하지 않은 단계를 완료로 표시하지 않는다.

## 독립 검토 반영

2026-10-11 Herdr의 별도 Codex가 목표·기술안·계획과 저장 관련 소스를 읽기 전용으로 검토했다. 가져오기 손실 전달, 복제 브라우저 탭의 복구본 소유권, 암호화·서명 상태, 형식 변경 저장 후 파일 연결이라는 네 항목을 계획에 반영했다. 복제 탭 동작은 코드 근거로 검사 과제에 추가했으며 런타임 재현을 완료한 것으로 취급하지 않는다. 계획의 문서·링크 검사는 수행하되 실제 브라우저·rhwp 실행과 Word·한컴 호환성은 P0/P1 이후 검증 대상으로 남긴다.
