# localhost 우선 개발·검증 계획

> 아래는 초기 개발 계획이다. 원본 클론 분리 이후 실행·검증 명령은 [루트 README](../README.md), 현재 검증 결과는 [통합 셸 검증 기록](validation/2026-10-11-integration-shell.md)을 따른다.

기준일: 2026-10-11

[최종 목표](project-goals.md)와 [구현 계획](implementation-roadmap.md)을 실행하기 위한 순서다. 첫 사용 환경은 localhost 웹앱이다. 사용자가 로컬 파일 작업을 확인하기 전에는 라이브에 배포하지 않는다.

## 현재 상태

소스·서브모듈·의존성 준비와 edentext 및 HOP Studio 호스트 빌드는 끝났다. 이는 통합 웹앱의 동작 확인이 아니다. rhwp 웹 임베드, 공통 저장, DOCX/HWPX 변환과 실제 브라우저 검증은 남아 있다. 확인된 환경은 [환경 준비 기록](environment-setup.md)을 참조한다.

## 개발 순서와 확인 가능한 결과

| 순서 | 구현 작업 | localhost에서 확인할 결과 | 기존 단계 |

| 2 | 독립 rhwp Studio 자체 호스팅, SDK/WASM 연결, 손실·revision 브리지 | HWP와 HWPX를 열고 본문·표를 수정해 각각 원래 형식으로 저장 | P1 |
| 3 | 새 문서 생성, 기본 본문·서식·표의 양방향 변환 실증 | 같은 작성 내용을 DOCX와 HWPX로 각각 저장하고 재열기 | P1 |
| 4 | 공통 세션·엔진 어댑터·파일 저장 트랜잭션 통합 | 하나의 앱에서 세 형식 열기, 원본 저장, 다른 이름 저장, 이후 새 대상에 재저장 | P2/P3 |
| 5 | 실패·취소·외부 변경 처리, 복구와 한글 입력, 기본 공통 UI | 아래 필수 시나리오를 통과하는 첫 사용자 확인본 | P4/P5 일부 |
| 6 | 고급 문서 요소·변환, 여러 문서, AI 기능 확장 | 최종 목표와 기능표에 따른 완성도 검증 | P4/P5/P6 |
| 7 | 배포용 빌드를 localhost에서 확인하고 사용자 검수 | 결과 보고서, 재현 절차, 알려진 제한, 배포 후보 산출물 | 배포 전 관문 |

단계 2·3은 실패 비용이 큰 기술 실증이므로 전체 UI 개편보다 먼저 한다. 초기 시연과 최종 제품 완료를 구분한다. 첫 사용자 확인본은 한 활성 문서와 기본 문서 요소로 시작하지만, 고급 요소·여러 문서 등 최종 목표를 삭제하지 않는다. P1 결과로 실제 작업량을 산정한 뒤 일정을 확정한다.

첫 구현 묶음은 ① 기준선 기록 ② rhwp의 웹 전용 빌드·정적 자산 경로 구성 ③ HWP/HWPX 원형식 저장 실증이다. HOP의 Tauri 전용 파일 접근을 웹 런타임에 복사하지 않는다. 고정된 upstream은 유지하고 제품 소유 빌드 구성과 명시적인 패치로 변경을 재현한다.

## 로컬 실행 구성

- 개발 주소는 `http://localhost:5173`, 배포용 미리보기 주소는 `http://localhost:4173`으로 고정한다. 포트가 사용 중이면 다른 프로세스를 종료하거나 자동으로 다른 포트로 옮기지 않고 충돌을 보고한다.
- 두 주소는 서로 다른 origin이다. 파일 권한·최근 파일·IndexedDB·복구 상태를 각각 검증하며, 두 주소 사이에 자동 이전된다고 기대하지 않는다. `localhost`와 `127.0.0.1`도 혼용하지 않는다.
- 사용자에게는 앱 주소 하나만 제공한다. rhwp Studio와 WASM·글꼴은 앱의 `/rhwp/` 경로에서 제공하도록 구성한다. 개발 프록시가 필요해도 브라우저에는 같은 origin 경로를 노출한다. 배포용 산출물에도 같은 자산 구조를 포함한다.
- 초기 전체 기능 검증은 현재 Mac의 Chrome에서 시작한다. Windows/macOS Chrome·Edge 조합은 배포 전 지원표에 따라 추가 검증한다. 미검증 조합은 지원 완료로 표시하지 않는다.
- 기본 문서 작업은 브라우저에서 처리한다. Python 검증 도구와 한컴·Word는 개발·호환성 검증에만 사용한다. 원격 rhwp 데모나 문서 업로드 서버를 실행 필수 조건으로 두지 않는다.

localhost는 보안 컨텍스트로 취급될 수 있어 지원 브라우저의 파일 선택 API를 로컬에서 검사할 수 있다. 실제 실행에서는 `isSecureContext`와 파일 선택 API 유무를 확인한다. 보안 컨텍스트 여부와 브라우저의 API 지원 여부는 별개다. 근거: [MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts), [showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker).

아래 명령은 현재 edentext 기준선 실행용이다. rhwp 통합 후에는 Studio 자산 준비를 포함하도록 제품의 빌드 절차를 확장하고 같은 주소에서 검증한다. 현재 명령만으로 한글 편집 기능이 추가되지는 않는다.

```sh
cd /Users/hwjung/Coding/edentext-word-hwp/source/edentext
volta run --node 24.21.0 npm run dev -- --host localhost --port 5173 --strictPort
```

배포용 로컬 확인은 빌드 성공 후 실행한다.

```sh
cd /Users/hwjung/Coding/edentext-word-hwp/source/edentext
volta run --node 24.21.0 npm run build
volta run --node 24.21.0 npm run preview -- --host localhost --port 4173 --strictPort
```

개발 시 반복 검사는 관련 타입·단위·브라우저 검사로 수행한다. 사용자가 확인할 때는 브라우저의 실제 OS 파일 선택기를 직접 사용한다. API mock이나 다운로드 파일 생성만으로 원본 저장을 통과 처리하지 않는다. 에이전트가 시험 서버를 실행할 때는 자기 프로세스를 추적하고 검증 종료 후 정리한다. 사용자 확인용 서버를 계속 둘 경우 실행 주소와 종료 방법을 인계한다.

## 첫 사용자 확인본의 필수 시나리오

원본 샘플은 보관하고 별도 시험 사본으로 검사한다. 각 형식에 본문·혼합 서식·일반 표·이미지 샘플을 준비한다. 이미지 등 아직 보존되지 않는 요소는 지원표에 명시하고 경고·원본 보호 동작을 검사한다.

| ID | 사용자 행동 | 통과 조건 |
|---|---|---|
| L01 | 새 문서에 한글 본문·서식·표 작성 → DOCX 저장 | 지정한 로컬 경로에 유효한 DOCX가 생기고 앱과 Word에서 내용 확인 |
| L02 | 같은 작성 내용을 HWPX로 다른 이름 저장 | 유효한 HWPX가 생기고 앱과 한컴에서 내용 확인; 첫 DOCX는 유지 |
| L03 | DOCX·HWP·HWPX를 각각 열어 수정 → 저장 | 선택한 원본 파일 자체에 수정이 반영되고 형식별 실제 프로그램에서 재열기 |
| L04 | 다른 폴더·이름으로 저장 → 추가 편집 → 저장 | 이후 저장은 새 파일만 갱신; 이전 파일의 해시는 변하지 않음 |
| L05 | DOCX↔HWPX 형식 변경 저장 → 편집 → 저장 | 실제 파일 형식과 확장자가 일치하고 새 대상에 계속 저장 |
| L06 | 선택기 취소·권한 거부·쓰기/닫기 실패 | 편집과 기존 파일 연결 유지; 저장 성공으로 표시하지 않음 |
| L07 | 저장 중 추가 편집·문서 전환·중복 저장 | 다른 문서에 기록하지 않음; 아직 저장하지 않은 최신 편집은 미저장 상태 유지 |
| L08 | 외부 프로그램으로 대상 변경, 동명 파일 두 개 열기 | 충돌 안내 및 별개 파일 식별; 잘못된 원본 덮어쓰기 없음 |
| L09 | 미저장 편집 후 새로고침·탭 복제·복구 | 최신 복구본 유지, 복제 탭 간 복구본 덮어쓰기 방지, 설정 준수 |
| L10 | 한글 조합 입력·붙여넣기·실행 취소·iframe 포커스 이동 | 글자 중복·누락 없이 편집하고 저장; 단축키가 현재 문서에 적용 |
| L11 | 지원하지 않는 요소·보호 문서 열기와 저장 시도 | 손실·보호 제한을 표시하고 원본을 조용히 손상시키지 않음 |
| L12 | 기본 열기·편집·저장 중 네트워크 확인 | 문서 원문 업로드와 원격 데모 의존 없음; 필요한 앱 자산은 로컬 제공 |

L01~L12는 첫 확인본 범위의 검사다. 최종 배포 후보는 전체 목표의 고급 요소·기능표와 기존 ODT 회귀까지 추가로 충족해야 한다. Word·한컴 환경이 없거나 OS 대화상자를 확인하지 못하면 해당 결과는 `미검증`으로 기록한다.

## 배포용 빌드와 라이브 전환

현재 `src/main.ts`는 프로덕션에서만 서비스 워커를 등록한다. 따라서 개발 서버 결과와 별도로 localhost 미리보기에서 다음을 검사한다.

1. 새 브라우저 프로필의 첫 실행과 기존 프로필의 새 버전 갱신을 모두 확인한다. `/rhwp/` 하위 HTML·WASM·글꼴의 경로·MIME·캐시를 검사하고 앱과 엔진 버전 혼합이 없는지 확인한다.
2. L01~L12의 핵심 저장 흐름과 복구를 배포 후보 산출물에서 재검사한다. 이전 캐시를 지워야만 통과하는 경우 갱신 결함으로 기록한다. 복구 확인 전에 브라우저 데이터를 삭제하지 않는다.
3. 결과를 `docs/validation/` 아래 실행일별 보고서로 남긴다. OS·브라우저·소스 커밋·자산 버전, 사례별 성공/실패/미검증, 파일 해시·내용 비교·화면 증거와 사용자 확인 결과를 기록한다. 개인정보 포함 문서는 보고서에 넣지 않는다.
4. 데이터 손실·잘못된 원본 저장·복구본 소실 결함은 0건이어야 한다. 필수 항목의 실패·미검증은 완료로 처리하지 않는다. 레이아웃과 성능 허용치는 P0에서 고정한 문서군 기준을 적용한다.
5. 사용자가 localhost에서 확인한 뒤 명시적으로 배포를 요청하면 배포 환경을 정한다. 먼저 HTTPS 시험 환경에서 경로·응답 헤더·캐시·파일 API와 재저장을 확인하고, 같은 검증 산출물로 라이브 전환한다. localhost의 권한·복구본은 운영 origin에 자동 이전되지 않는다.

이 문서는 실행 계획이며 브라우저 검증 결과 보고서가 아니다. P1의 한글 검증 화면 구현과 자동 브라우저 검사는 [첫 구현 결과](validation/2026-10-11-p1.md)에 기록했다. 전체 통합 기능, localhost 사용자 검수와 라이브 배포는 아직 완료하지 않았다.
